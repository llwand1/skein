先回答：我们的"上下滑"是什么

抖音把一切行为浓缩成一个动作：上下滑。用户永远知道"我在干什么"。本项目也必须能一句话说清核心动作，否则就是"看不懂怎么用"。
核心动作＝喂。你正常上网，看到合适的内容，划一下、喂给这一期缺的那一项。
这一个动作同时做完两件事：存下原文（这条素材的证据）＋ 勾掉一项欠账（清单少一项）。
换句话说：清单不是要你手动去填的待办，而是一排"等着被喂"的槽位。

对照抖音：状态层＝视频一直在播（不用点）；动作层＝上下滑（一个动作看下一个）；收口层＝看完一个视频（明确的结算）。三层各有其"一个动作"，不混。

为什么这样设计——用户在任何一刻都不该迷路

  • 球从不主动找你，只有"未完成"在找你。不做推送轰炸；2/4 这个数字就是提醒本身。
  • 喂素材不离开当前页面。参照词镜的产品命题"问题发生在哪里，就在哪里解决"——化为本项目就是"看到好东西的地方，就是喂它的地方"。
  • 每次喂完都有回执。进度 +1、该项打勾、原文存档、球环推进——"我刚完成了什么"必须看得见。
  • 齐了才出现"发布"。按钮出现本身就是信号：你已经攒够可以发了。
这三条正好回答你那句"看不懂怎么用、不知道在干什么"：任何时刻，界面都要能替你回答"我在干什么 / 还差什么 / 下一步做什么"。下一 Tab 让它实时跑给你看。

关于 MCP，真正新的那一点在哪

很多人第一次看 MCP，会把它理解成"又一种函数调用"。这个理解不算错，但它解释不了一个事实：为什么大家已经能用 function calling 把模型接到自己的数据库上了，还非要再套一层协议。

要回答这个问题，得先承认 function calling 解决的只是"模型如何表达它想调用什么"。它是一个模型侧的约定，至于那个函数在哪里、怎么被找到、谁有权限调、调用过程怎么被观测 —— 这些它一个都没管。

真正的差别在于：协议把"发现能力"和"使用能力"这两件事标准化了。工具清单可以被询问、可以被列举、带着输入模式返回；宿主不必在编译期就知道世界上有哪些工具。

反过来看边界也清楚：它不负责模型好不好、不负责推理质量、也不替你做权限判断。把它当万能钥匙会失望，把它当"集成层的最小公约数"则刚好。
