为什么顺序必须反过来

这不是审美问题，是「用球验什么」的问题。
要验的事球验得了吗说明
闭环价值：给了清单，你浏览时会不会真的顺手喂、能不能攒齐、攒齐后能不能真发出去验不了球不影响「你喂不喂」，只影响「你会不会想起来」。用一个不影响结果的变量去验收，结论必然失真。
清单质量：生成的清单是不是这一期真正缺的东西验不了清单错了，球再醒目也只是让你更快攒出一堆没用的素材。
载体价值：没有球会不会忘了这件事、会不会半途而废只有这个能验这才是球的变量 —— 它是后置的，因为要等闭环被证明值得做，才轮到优化载体。
一句话：先证明这件事有用，再让它变轻。反过来做的话，最可能的结局是「球做得很好看，清单一次也没攒齐过」。

P0 的验收判据（先证明有用）

  • 真主题、真素材、真发布。用一期你真打算发的主题跑完，不是测试主题 —— 用假主题跑，整圈的价值无从判断。
  • 出口物判据：攒齐的素材能不能直接进排版。判据不是「清单打勾打完了」，而是「把这 4 项素材丢给排版，能不能不再回头找资料」。

纠正之后，方向反而更清楚了

这一条是这次纠正里最有价值的推论。
如果词镜的主体真是「系统级融合」，那么 task-orb 的终极形态也不是悬浮球 —— 球只是「把未完成钉在你眼前」的提醒器，甚至是过渡形态。真正的方向是：让喂素材这个动作融进你本来就在做的浏览行为里，不要求你先打开任何东西。
  • 这恰好解释了为什么球该后置：它是提醒载体，作用在「你会不会想起来」；而 P0 要证的是「这一圈能不能攒出一篇」—— 后者成立与否，跟球一点关系都没有。
  • 也解释了 P-007 的「轻」到底在说什么：不是「窗口小」，是「不要求用户发起一个使用动作」。用这个口径看，一个必须点击才能用的球，本身就还不够轻。

给自己立的判据（防止下次再犯）

写下来是因为这类错误会重复发生，靠记忆拦不住。
  • 判据一：说「可复用」之前，先回答「我复用的是它的主体还是它的一块皮」。浮层、卡片、面板都是皮；接入方式、原则、数据边界才是主体。
  • 判据二：「可复用」不能决定「优先级」。优先级只能由需求本身决定 —— 哪怕某个能力 100% 能复用，只要它不属于当前要验的那件事，就不该排在前面。
  • 判据三：参照一个既有产品前，先读它的产品命题（宪法级）章节，再读实现。这次我先读了实现与验证数，跳过了命题，所以把手段当成了目的。

关于 MCP，真正新的那一点在哪

很多人第一次看 MCP，会把它理解成「又一种函数调用」。这个理解不算错，但它解释不了一个事实：为什么大家已经能用 function calling 把模型接到自己的数据库上了，还非要再套一层协议。

要回答这个问题，得先承认 function calling 解决的只是「模型如何表达它想调用什么」。它是一个模型侧的约定，至于那个函数在哪里、怎么被找到、谁有权限调、调用过程怎么被观测 —— 这些它一个都没管。于是每个客户端都要为每个数据源重写一遍集成。

真正的差别在于：协议把「发现能力」和「使用能力」这两件事标准化了。工具清单可以被询问、可以被列举、带着输入模式返回；宿主不必在编译期就知道世界上有哪些工具。

反过来看边界也清楚：它不负责模型好不好、不负责推理质量、也不替你做权限判断。把它当万能钥匙会失望，把它当「集成层的最小公约数」则刚好。

所以对使用者的实际结论是：当你只有一个数据源时，它几乎没有价值；当你要把同一份能力接进多个不同的宿主时，它的收益才开始显现。

架构结论先行（v0.4 修正：栈不定）

上一版给了「推荐方案 A/B/C」，被老板否掉了 —— 定位没钉之前不该定栈。本版只保留现在就能确定的客观约束，其余改为条件表。
现在能定的只有一条：这是个分层的东西，其中「采集层必须进操作系统」。其余（主栈、UI、进程模型）一律等定位钉清后再定，一步步来。
能确定的第二条：它确实是三种性质完全不同的活 —— 采集碰操作系统、组织碰数据、发布只是跳个 URL。硬塞一个栈，只会让最简单的部分被最难的部分拖着走。

为什么现在不该定栈

这条是老板的裁定，理由是「可以等产品定位然后一步步决定」。补上理由的那一半。
  • 栈是定位的函数，不是自由的。「个人自用工具」和「要给别人跑的 AI 应用」需要的栈几乎不重叠；定位没定就选栈，等于在猜答案。
  • 但有一条例外：先跑一个可行性探针不算定栈。如果某条栈有致命不确定性（例：Rust 下 TSF/COM 的 bindings 稀缺），可以在定位定清前先探一下，探完就知道这条要不要从候选里划掉 —— 这是排除，不是选定。
  • P0 完全不受影响。P0 是跑通工作流，土载体即可；栈定不定都不阻塞它。

Java 方向的内部候选（条件表，未定）

老板问「Java 有没有更适合的」。Java 不是单一选择，下面四个的适用定位完全不同 —— 所以没法在不谈定位的前提下推荐。
候选适合什么定位代价
Spring Boot 定位是「求职用的 AI 应用代表作」；且要与你正在做的模型用量网关联动成体系 启动慢、常驻内存大（对个人小工具偏重）。但 JD 命中最高——Spring 在 AI 应用岗是硬通货。
极轻框架
Javalin / Spark Java
 定位是「自己每天开着的轻工具，顺带是 Java 作品」：单 jar 几 MB、秒起、本地服务 + 浏览器工作台 简历上不够「企业级」。但能写成一篇 ADR（「为什么不上 Spring Boot」）—— 你在网关项目里已认定这类决策记录是加分动作。
Quarkus / Micronaut 定位是「要 Java 但要轻、甚至要原生镜像」：启动快、内存小 生态与资料少于 Spring，JD 命中低（写 Quarkus 不如 Spring Boot 被认）。
JavaFX 定位是「纯桌面应用」且要单一语言 系统级 hook 要走 JNI，复杂度跳一档；桌面分发重（内嵌 JRE）。
注意一个反直觉的点：Spring Boot 和极轻框架的分歧不在技术，在「这个作品要给谁看」 —— 给面试官看选前者，给自己每天用选后者。所以它是定位问题。

五个定位变量，各自怎么决定栈

定位钉清 = 把这五个问题答完。答完之后栈基本是唯一解，不需要「选」。
定位问题答法 A → 栈倾向答法 B → 栈倾向
① 它给谁用 只给自己 → 极轻、单文件、能跑就行；分发可以不解决 要给别人看/跑 → 必须解决分发（打包/安装），栈要选「别人装得上」的
② 要不要联网/多端 纯本地 → 不需要真正的服务端，Java 后端价值下降 要多端/同步 → 必须有服务端，Java 后端才真正有意义（这是 Java 方案成立的前提）
③ 简历上代表什么能力 后端工程（Spring/并发/SQL/接口封装）→ Java 系统级/桌面能力（钩子、COM、不抢焦点）→ 原生栈（Rust/C#），Java 反而不合适
④ 要不要与网关联动 联动（AI 调用走自己的模型用量网关）→ 服务化，Java 天然合适，且两项目互证成体系 独立（自己直接调模型）→ 无所谓栈，轻便优先
⑤ 「多平台」是真做还是只跳转 只跳转（当前红线下的现实）→ 平台=字段，不需要抽象层 将来真接入 → 才需要平台适配架构，且那时才值得为它选栈
其中 ② 和 ③ 是最强的两个：只要「不要服务端」＋「代表系统级能力」，Java 方案就应该整个划掉 —— 那时该走原生栈。反过来只要「要服务端」＋「代表后端工程」，Java 就是唯一合理的主栈。

最重要的一条判断：「多平台」现在是个字段，不是一套架构

这条如果不先钉死，架构会立刻膨胀成一堆永远不会被调用的适配器。
听起来要做的实际能做的（受限于红线）所以架构上该做的
接入抖音 / 小红书 / B站 / 微信 微信个人号无官方 API（协议登录必封）；抖音私信接口只对认证企业号开放 —— requirements §3 已列为红线 不做平台适配器。「平台」退化为一张表：名称 + 发布页 URL + 文案规格差异
一键发布 只能跳到发布页；发送永远真人（P-001 原话） 执行器只有 open_url 一个动作，没有写操作客户端
评论/私信监测 P2 才碰；且只做「提醒 + 给草稿」，不做代回 预留数据字段（平台名、来源 URL），不预留抽象接口
判据：等真的出现第二个平台、且两者行为确实不同时，再抽抽象层。现在抽，抽出来的形状一定是猜的 —— 这是最容易白做的一类架构。

候选池（不作推荐，只记排除条件）

按「多个简单方案组合」而不是「一个复杂方案」的思路列着。选定要等定位钉清；这里只写「什么情况下这条该被划掉」。
#候选内容什么情况下划掉它
① 分层选型 L1 原生（语言待定）；L2 SQLite；L3 本地 Web 工作台 + 原生常驻小窗；L4 兼容接口 若定位定为「纯本地、不要服务端」且要单一语言 → 分层带来的多语言成本不划算。
② Java 主体 + 薄原生采集端 工作流/数据/AI 编排用 Java；采集端另起小进程（复用现有 Python 或另写） 若定位定为「不要服务端」或「代表系统级/桌面能力」 → 整个划掉（那时 Java 无处施展）。
③ 原生单栈（Rust / C#） 采集与 UI 一条栈打通，无服务化 若定位定为「要服务端/要与网关联动」→ 划掉；另 Rust 在目标 JD 上命中低，且 TSF/COM bindings 稀缺（需先过探针）。
④ 全 Python + Tk 单一语言、单一栈，心智负担最小 若定位要求「构成新的代表作」 → Python 已有代表作，直接划掉。另：工作台富交互（表格+长文+缩略图）用 Tk 做会很痛。
有一条与候选无关的硬约束仍然成立：把「最难且不确定的」（采集）和「最简单但会变的」（界面/工作流）分开。无论最后选哪个候选，这两块都不该绑死 —— 采集万一走不通，其余部分还能活。

  • 禁止 任何平台的写操作客户端。代码里不存在通往「发送」按钮的路径，只有通往「打开页面」的路径 —— 这条在架构层就要卡死，不能靠调用时自觉。
